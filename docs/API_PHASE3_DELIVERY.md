# Python 后端升级：阶段三交付

日期：2026-10-22。已完成 PostgreSQL、SQLAlchemy、Alembic、账户工作区及旧历史归属迁移，当前 Docker 服务已切换。原作者、来源和 MIT 许可证保持不变。

## 使用变化

打开 <http://localhost:8501> 先登录，再上传表格分析。当前部署者用户名为 `owner`；初始随机密码只保存在数据卷 `.bootstrap/owner.json` 和本机 `.runtime/phase3/owner_credentials.json`，没有写入本报告或源码。登录后可在侧栏验证旧密码并修改密码；修改会撤销全部会话，初始凭据文件不会同步更新。

每个账户只访问自己的上传、原件、任务、报告、字段映射和对话。Agent 比较和查原文也在所属工作区内；旧共享 `APP_API_TOKEN` 在账户模式中不能读取业务数据。账户由部署者通过 CLI 创建，没有公开注册。新账户不会自动看到旧报告。

阶段二的合并分析、后台运行、取消与安全恢复继续可用，所选工作表上限仍为 1,000 行、5 MB；不会自动处理其他工作表。页面历史管理与 Agent 的部分能力仍在服务器调用已认证的仓库服务，尚未全量改为 HTTP 客户端。

## 后端实现

| 文件 | 作用 |
| --- | --- |
| `backend/database.py` | 共享 SQLAlchemy Base、连接池、生产 PostgreSQL 校验、UUID 工作区目录与符号链接防护 |
| `backend/accounts.py` | Argon2id 密码、只保存摘要的会话、8 小时过期、退出撤销、验证旧密码后改密、共享登录限流 |
| `alembic.ini`、`migrations/` | 显式 12 表基线，空库升级、独立测试 schema 降级重建、与当前模型一致性核对 |
| `backend/pg_history.py` | 按工作区查询的历史/字段映射、复合唯一约束、验证原件、事务对话追加、工作区备份 |
| `backend/pg_jobs.py` | 关系化任务、分组、逐行结果、请求尝试、幂等和 Outbox；复合外键与有范围的业务仓库 |
| `backend/tenancy.py` | HTTP 从认证身份选择仓库；Worker 从数据库任务的 scope 选择历史及原件目录 |
| `backend/app.py`、`schemas.py`、`service.py` | 登录/退出/改密接口、请求前会话校验、全部数据路由按当前工作区绑定、分页、并发聊天追加 |
| `app.py`、`backend/client.py` | 登录页、退出清除会话私有数据、改密及用户任务凭据，旧单工作区模式保持兼容 |
| `backend/manage.py`、`import_legacy.py` | 不输出密码的部署管理、明确归属账户的只读旧历史迁移、摘要/ID 保持与冲突拒绝 |
| `compose.accounts.yml`、依赖锁、配置模板 | PostgreSQL 17、一次性 Alembic 初始化、沿用原业务卷；数据库不映射宿主端口 |
| `tests/test_accounts.py`、`test_account_api.py`、`test_account_ui.py`、`test_pg_history.py`、`test_pg_jobs.py` | 账户、权限、迁移、并发对话与任务恢复测试 |
| `tools/verify_account_queue.py`、`account_acceptance_worker.py` | 实际 PostgreSQL/Redis/Celery 的双账户隔离验收，模型由测试工具内注入模拟响应 |

SQLAlchemy 同时使用声明式模型与 Core 事务；未宣称所有服务已改写为 ORM Session。任务库复用既有状态机，使用明确的 SQL 绑定适配和 PostgreSQL 事务锁，避免重新实现一套不同的费用恢复规则。生产请求不自动建表，Schema 变化由 Alembic 执行。

全局每日模型额度仍保留原 SQLite 台账，避免旧占用在升级后清零；Redis 请求令牌继续约束分析与 Agent。此版本仍按单机共享数据卷部署，尚未完成多节点扩容。

## 验证结果

完整离线回归运行 **640 项，625 项通过、15 项跳过，700.942 秒，退出码 0**。跳过项为未指定真实 PostgreSQL 时的 13 项账户/迁移测试、1 项 PG 并发测试，以及 Windows 账户不能创建符号链接的 1 项路径测试。真实 PostgreSQL 测试已在独立 UUID schema 另外执行，没有在生产库执行降级。

| 真实 PostgreSQL 专项 | 结果 |
| --- | --- |
| 账户、限流、会话、迁移一致性及降级重建 | 13 项通过 |
| 历史隔离、并发追加、原件与只读旧库迁移 | 13 项通过 |
| 任务状态机、幂等、500 行检查点、租约、复合外键及跨实例并发 | 34 项通过 |

这些专项与完整回归存在覆盖重叠，不相加冒充独立测试总数。新账户 UI 8 项测试包含在完整回归，验证未登录不显示旧数据、登录与退出清除私有状态、到期重登录、工作区取自服务器身份及改密行为。

实际容器验收使用独立内部网络、专用 Linux 命名卷和无效的固定模型地址/密钥，不读取实际 `.env`，不发送私人表格。保留生产的 `default_worker → TenantJobWorker → 有范围的 PostgreSQL 仓库` 路径，只在工具中替换 SDK；生产没有 Mock 环境开关。

代码编译、锁文件同步及 Python wheel 构建通过。部署镜像的 27 个业务源码、迁移及依赖文件摘要与最终工作区逐一相同。浏览器实际打开登录页确认未登录时无上传、历史或原表内容；实际 HTTP 使用临时 owner 会话核对旧报告后已撤销该会话。

## 现有数据迁移与部署

迁移前确认旧任务库为 0 个任务；该导入器遇到非空旧任务库会拒绝切换，不会静默丢失任务。停止旧 UI/API/Worker/投递器写入，保留历史 ZIP、原请求额度和任务库快照后，将两份历史及两份字段映射显式导入 `owner` 工作区。

导入保留原批次 ID、原始时间、原表、报告及聊天的序列化摘要；再次核对返回两份均已存在、无需新增。旧 SQLite 库与原件保留，报告、原件和对话内容未更改。原 `.env` 的模型与既有配置保留，只补充缺少的 PostgreSQL 凭据；连接地址由账户 Compose 层注入，不会让本机旧模式回归测试自动连接生产库。

实际 HTTP 验收读取 **2 份报告、105 条原始记录、98 条有效分析**，验证两份聊天、四个 CSV/HTML 下载与原件摘要；上传原件后在 `allow_model_call=false` 下通过新任务接口复用两份报告，均命中缓存，没有创建付费分析。证据见 [existing_history.json](../validation/backend_phase3/existing_history.json)。旧库、原件、对话及全局额度台账的升级前后摘要完全相同。

用户那份 500 条文件仍只分析过其中一张 100 条工作表，其余 400 条没有自动分析。新增验收的 520 条都是独立合成数据，未导入用户工作区，也不构成真实模型效果评测。

当前 UI/API/PostgreSQL/Redis 健康检查通过，Worker 日志确认 ready，独立投递器已运行。HTTP 健康探针仍只证明进程可访问，没有声称完整队列或模型就绪。其他既有服务未更改。
