# CustomerInsight 演示调研与升级建议

调研日期：2026-10-25。范围为公开 GitHub 仓库、官方 README、部分源码，以及本项目的当前实现。本次交付是调研与方案，未安装参考项目、未改动运行服务、未产生真实模型请求。

## 结论

现有上传、后台任务、历史记录、主题、原文工具和多轮问答足以支撑演示。当前最值得提升的是把这些能力连成一条业务路径，让用户快速完成“发现问题 → 核对原文 → 追问 → 比较批次 → 带走报告”。

优先建设可完整体验的示例工作区、图表与原文联动、问答中的图表输出，再改善主题一致性和等待反馈。以下建议是本项目的产品判断，不是参考项目对我们的性能或效果背书。

需要区分参考范围：Vanna 的仓库页面标注已于 2026-03-29 归档，只参考其交互设计。WrenAI 当前 README 将旧聊天 BI 界面保存在 legacy 分支，并区分开源引擎与商业 UI；这里主要借鉴指标语义管理。Formbricks 的业务入口与反馈组织方式值得参考，本次没有把其全部分析能力认定为免费开源功能。

另查看了 [RATH](https://github.com/Kanaries/RATH)（约 4.7k Star）的自动探索与推荐可视化思路，与 PyGWalker 的参考点重叠，不作为新增依赖。

### 源码层面的具体启发

- [LIDA 的 GoalExplorer](https://github.com/microsoft/lida/blob/main/lida/components/goal.py) 把一个目标组织为问题、可视化和理由，并要求使用摘要中实际存在的字段。我们可以把推荐追问也做成有数据条件的结构，而不是向所有表格显示同一组问题。
- [PyGWalker 的 StreamlitRenderer](https://github.com/Kanaries/pygwalker/blob/main/pygwalker/api/streamlit.py) 区分图表规格、保存路径和筛选条件。我们的筛选状态也应结构化保存，而不是把筛选条件只留在图表组件里。
- [PandasAI 的 Agent](https://github.com/Sinaptik-AI/pandas-ai/blob/main/pandasai/agent/base.py) 区分新对话与 follow_up。我们已经有多轮对话，不需要再实现一次；要补的是回答结果类型与可视化展示。

## 当前实现与实际缺口

| 能力 | 当前状态 | 对演示的影响 |
| --- | --- | --- |
| Excel/CSV、工作表与列映射 | 已有；生产路径经后端预览与提交 | 可以复用，不重建上传流程 |
| 图表与一句话总结 | 已有 | 可作为进入结果页后的第一屏 |
| 具体主题与引用原文 | 已有前三主题及原文展开，主题可预填追问 | 已有证据基础，重点改善联动 |
| 多轮 LLM 与查表工具 | 已有 11 个白名单工具，包括原文检索和历史查询 | 应在演示中明确展示一次真实工具查询 |
| 历史基础统计与主题比较 | 已有，主题缺失不再阻断基础统计 | 同一业务两批数据可直接展示 |
| 导出与持久化 | 已有 CSV、离线 HTML 和对话下载 | 不把“增加导出/历史”当作本轮新功能 |
| 示例入口 | 单份已保存报告；示例模式直接禁用 Agent 和历史选择 | 用户无法体验最有区别的追问与跨批查询 |
| 图表交互 | 以悬停为主 | 点图不能直接筛出原文并继续问 |
| 问答结果类型 | 正文与引用；尚无受限图表规格 | 用户请求画图时，回答表现力不足 |
| 等待过程 | 后台任务需手动刷新；问答整轮 spinner | 容易让观众误以为卡住 |
| 主题一致性 | 按 kind 与原样 topic 组合分桶 | 同义词可能拆分，跨批主题难对齐 |

代码依据：`app.py` 的 `_load_demo_report`、`_render_analysis_agent`、`render_customer_report`、`_render_history_comparison`、各图表渲染函数；`core/analysis_agent.py` 的 `AgentQuery` / `FreeformAnswer`；`core/review_topics.py` 的主题聚合。当前首页已有“分析结果 / 问 Agent / 明细与下载”三个标签，不建议再增加大量一级菜单。

## 建议实施顺序

### 第一批：让人能完整体验

1. **两批示例工作区。** 一个业务场景，提供两批评价、保存的分析、原文和两轮问答。示例的界面路径与正常报告一致。明确标注“已保存演示”，自由输入新问题走显式的实时调用；查看回放不伪装为正在调用 LLM。不直接去掉现在的 `is_demo` 防线，而是为示例定义独立的数据、对话与权限范围。
2. **主题/图表 → 原文 → 追问。** 点击某个主题或柱状条后，图表和原文列表采用相同筛选条件，并提供“哪些评价能说明？”、“哪个产品更集中？”等快捷入口。传递的是结构化筛选范围，Agent 查询时仍按服务端权限和批次范围校验。筛选、展开、切换页面不触发模型请求。
3. **推荐问题。** 有产品或门店列才推荐比较问题；有可识别日期才推荐时间问题；选定上一批才推荐批次问题。首屏最多三个入口，每个入口直接反映当前数据里可分析的事情。

建议代码入口：`app.py` 示例加载、主题卡片、图表、明细、聊天组件；新增一个小型演示数据加载模块，复用现有报告构建与序列化，不绕过账户隔离或将生产历史当公共样例。

### 第二批：让回答更有信息量

4. **回答附图与可下载简报。** 用户问“各产品的物流问题占比如何”，回答给出简短解释、条形图、分子/分母与可展开的原文。模型只选择受限图表规格，程序通过已获准工具的实际数据计算与渲染；不开放任意 Python/SQL 执行。明确“当前筛选”还是“全部有效评价”。将所选回答和图加入导出简报，复用既有 HTML 报告能力。
5. **稳定主题名称。** 先建立可审计的主题 ID 与同义映射，把“配送慢/物流延迟”映射到统一的延迟主题。保留原始提取词、每行证据与映射版本；同一原记录在一个归一主题中仍只计一次。问题、需求与认可保持区分。跨批比较只对兼容的主题版本计算变化，无法对齐时保留已有基础统计比较。

建议代码入口：`core/analysis_agent.py` 的输出模型与校验、`core/agent_table_tools.py` 的汇总能力、`core/review_topics.py`、`app.py` 的结果渲染、`core/report_visuals.py` 的导出。不要默默重写历史报告或自动重跑模型。

### 第三批：让现场演示稳定

6. **实际进度与平滑等待。** 分析任务低频自动刷新；问答展示真实的“读取统计 / 查询原文 / 生成回答”阶段、工具名称和用时，不生成虚构的思考过程。结构化结果先通过校验，再呈现可引用的图表与统计。流式文本可后续加入，不应因追求逐字输出绕过校验。
7. **面向演示的首页与说明。** 主入口只保留“上传表格”和“体验示例”；首页结果以一句结论、关键指标、三个具体主题开场。部署、历史实验和测试证据放在工程文档，单独提供精简演示说明，避免 README 的历次交付内容遮住首次体验。

## 演示数据方案

目前公开样例是 UCI 的历史英文评价摘录，适合证明真实文本接入、分析与导出通路，但没有真实的门店、评价日期或销量字段。来源与抽样限制已经写在项目内 `datasets/public_reviews/DATA_SOURCES.md` 和 `metadata.json`。

为中文演示建议另外准备一个明确标注的电商售后或餐饮门店场景：两批各 30-50 条、字段稳定，包含几个能从原文核对的主题。若使用合成中文评价、虚拟产品/门店或模拟日期，必须明确标为演示数据。真实公开英文数据保留为独立入口，不能给它补造业务字段后宣称是真实经营数据。

批次 A/B 只能证明两次上传的差异。没有真实时间、同样的采样口径和其他业务证据时，不能将差异描述为改善趋势或措施带来的效果。当前 500 条表格仍可用于规模与分组处理演示，不必为了录制反复调用模型。

## 三分钟演示脚本

| 时段 | 操作 | 让观众看见的价值 |
| --- | --- | --- |
| 0:00-0:25 | 打开一个明确标注的示例工作区，或上传小表 | 不用设计提示词即可得到结果 |
| 0:25-0:55 | 看总结、主要主题、产品/门店分布 | 能快速定位要关注的具体问题 |
| 0:55-1:25 | 点某个主题，核对两三条原文 | 结论能回到原始行核查 |
| 1:25-2:00 | 问“哪个产品最集中？请给图和依据” | Agent 查询表格后给解释、图和引用 |
| 2:00-2:35 | 追问“上一批也存在这个问题吗？” | 对话理解上下文，查询选定历史批次 |
| 2:35-3:00 | 导出当前范围的简报 | 有可分享、可复核的实际成果 |

以上是升级后的目标脚本，当前版本尚未实现所有环节。现场只做少量实时问题；较慢的批量分析预先完成，明确说明是已保存结果。

## 验收要点

- 不填 Key、不发请求也能走完已保存演示；回放与实时体验清楚区分。
- 任意点击图表后，图表、列表和追问展示同一批次、同一范围；清除筛选可恢复。
- 推荐问题不引用不存在的列、日期、历史批次或外部业务信息。
- 图表数值由真实查询结果计算，能核对分子、分母与原始记录；非法图表规格被拒绝。
- 两个同义主题合并后按原记录去重，原词与证据不丢失；历史主题版本不兼容时有明确反馈。
- 示例数据、用户数据、对话和历史批次互相隔离；不得借演示模式公开真实账户历史。
- 刷新、筛选、下载和查看回放不新增模型请求；中断或服务不可用时保留已保存成果。

不建议为这次 demo 重写整个前端、替换后端框架或直接接入大型 BI 引擎。先用现有架构实现上述交互；如果以后增加“自由探索”，再评估将 PyGWalker 作为可选页接入。
