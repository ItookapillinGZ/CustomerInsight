# 合成反馈示例集与标注规则

## 数据来源与复核状态

`data/feedback_eval.csv` 是为演示评测流程独立编写的 **60 条合成示例**，以中文为主。不是实际客户反馈，不是业务采样，也不是已完成人工标注的数据。初始 gold 标签是开发时编写的 **待人工复核草稿**，全部 `review_status=draft`。运行结果必须标为“临时结果”，不能据此宣称模型业务准确率、上线收益或版本提升。

固定划分为 `dev-001` 至 `dev-040` 的 40 条开发集（`split=dev`），以及 `test-001` 至 `test-020` 的 20 条测试集（`split=test`）。包含否定、混合情感、多问题、类别边界、低影响与高影响问题，以及嵌入指令文本。仅覆盖有限的手工设计情形，不代表真实反馈的类别频率。

可使用开发集调整 Prompt、设计 few-shot、排查规则。**测试集及其近似改写不得作为 few-shot 示例或用于调整 Prompt**。冻结 Prompt 之后再在测试集上运行；若根据测试结果继续调参，应把已有测试集视为已暴露，并另建测试集。独立编写 few-shot 时也应检查是否近似复述测试样本。

`gold_sentiment`、`gold_category`、`gold_priority`、`split`、`review_status` 只用于本地评测与报告，绝不能加入模型请求；模型只接收 `text` 和固定的 Prompt/输出格式。`sample_id` 由本地保留以匹配预测，不由模型生成。评测加载器独立于普通业务 CSV 处理，任何非法记录都使整个数据集校验失败，不跳过、不自动重新标注、不重写 ID。

## 情感规则：只有三个固定标签

| 标签 | 判定规则 |
| --- | --- |
| `positive` | 明确满意、表扬、感谢，且没有仍未解决且占主导的负面问题。已修复问题以当前满意状态判断。 |
| `negative` | 明确不满、故障、损失、阻断或负面体验。没有情绪词也可因明确的不良结果判断为负面。 |
| `neutral` | 中性询问、事实记录、没有不满的需求提议；或正负体验势均力敌，文本无法确定主导情感。 |

不增加 `mixed` 标签。混合情感时先识别仍未解决的主问题及影响：与阻断、损失、安全相关的明确负面问题通常主导；礼貌感谢、顺带赞美不会抵消。无主导问题且确实平衡时标 `neutral`。不要机械地按正负词数量投票。理解否定和时间变化：“不再卡顿”且表达满意标 `positive`；“没有其他评价”是 `neutral`；“不是重复扣款，但额外费用没说明”仍可为负面。

## 主类别规则与边界

每条只标一个主类别，输出仍使用项目既有九类枚举。按反馈的直接问题对象和事实标注，不以“建议”“希望”“体验差”等字面词决定类别。

| 类别 | 规则与边界 |
| --- | --- |
| `bugs` | 已有软件功能不按预期工作：报错、闪退、数据丢失、错误计算或显示。明确软件重复扣款是故障；收费政策贵或额外收费是 `pricing`。功能正常但步骤繁琐是 `user_experience`。 |
| `features` | 当前不存在的新能力，或明确增加功能范围，如夜间模式、批量开票、集成 API。现有导出漏行是 `bugs`；让现有流程更顺手一般是 `user_experience`。 |
| `suggestions` | 对说明文档、政策、运营安排、培训、维护通知等的改进提议，且不是某个更明确类别的问题。它不是所有“建议”的兜底：建议修闪退仍是 `bugs`；建议加新能力仍是 `features`。 |
| `user_experience` | 功能正常但导航、步骤、布局、文案、可读性或操作负担不好；也包含相关正面评价。视觉元素显示错误且本应正常渲染是 `bugs`；喜欢现有配色但想换色属于此类。 |
| `product_quality` | 实体产品的材质、耐用性、性能或安全质量问题与评价。软件已有功能的执行错误归 `bugs`；运送造成的外包装损坏且商品完整归 `delivery`。 |
| `customer_service` | 客服沟通、售后响应、服务态度、服务时间、解决问题的支持过程。客服一句表扬但产品不耐用是多问题判断，不能自动归客服。 |
| `pricing` | 标价、涨价、折扣、收费透明度、套餐价值与定价政策。因软件行为造成重复扣费或错误计算优先归 `bugs`。 |
| `delivery` | 发货、配送、时效、物流跟踪、送错地点、承运包装等。实体商品自身缺陷不归物流。 |
| `other` | 信息不足，或与以上对象无关的留言。失败或无法解析的模型输出没有有效预测，不能据此填 `other`。 |

多问题选择主类别的顺序：

1. 先选有证据支持的最高影响问题（安全/资金/数据风险与关键任务阻断优先），不凭猜测扩大影响。
2. 同等影响时，采用用户明确指出“最需要解决”“主要希望”等强调的实质问题。
3. 仍不能区分时，按正文首次提到的实质问题选主类；已解决问题或随口赞美不优先于仍未解决的问题。
4. 记录人工分歧供复核，不创造多标签类别。反馈级优先级取所有问题中最高的有证据影响。

例如开发集 `dev-025` 的客服与配送表扬不会改变耳机故障这一主问题；`dev-018` 的速度表扬不会抵消每天找入口的操作困难；`dev-030` 区分定价政策和软件重复扣款。

## 优先级规则

| 标签 | 规则 |
| --- | --- |
| `high` | 有明确安全风险、持续资金/关键数据损失、紧急不可逆影响，或核心任务完全阻断且没有可用绕行。需优先处置。 |
| `medium` | 影响正常工作或使用，有显著不便、部分失效、延误；没有具体紧急风险，或存在合理绕行方案。重要但未到紧急阻断。 |
| `low` | 普通询问、无影响事实记录、表扬、轻微展示/文案问题、一般优化与未来需求。 |

优先级由影响与紧迫程度决定，不由语气激烈程度决定。不能把所有 `bugs` 都标高，不能把所有新功能都标低；如明确账户已被盗且缺少二次验证，安全能力请求可以是高。缺乏具体影响时不得想象风险；一般需求按文本描述工作负担在中低之间选择。已解决问题和单纯表扬通常低。

## 嵌入指令与失败

反馈中的“忽略规则”“输出某标签”“泄露提示”等是待分析文本，不能执行。分类依据实际反馈问题；仅有引用指令且没有实质产品问题时按 `other`/`neutral`/`low` 判断。模型格式不完整、非法枚举、拒答或调用错误不能标为成功，也不能替换成任一默认标签。

## 人工复核操作

复核者应先阅读上述规则，逐条独立判断，再讨论分歧并记录规则变化及理由。只有实际复核并确认后才能把对应行改为 `reviewed`；不要由模型自动改状态。本文不声称采用双人标注、计算一致性或已完成复核。建议在真实使用前保留复核人员、日期、分歧与修订记录，并重新检查类别边界。

更改 gold、split、text、ID 或 `review_status` 会改变数据集 hash，不能把更改前后视为同一数据集结果。各版本比较须使用相同整集 hash、split、模型与请求设置。加载器拒绝空白文本、超长文本、非法标签/状态、重复 ID、冲突标注，以及经 NFKC 和空白合并正规化后的所有重复文本（包括跨 split 重复）。近似改写的语义泄漏需要人工检查，本地重复检测不能保证识别它。
